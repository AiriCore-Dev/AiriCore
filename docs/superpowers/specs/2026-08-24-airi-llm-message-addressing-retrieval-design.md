# airi_llm 消息聚合、上下文受话判断与统一检索设计

## 目标

解决 `airi_llm` 的三个行为问题：

1. 同一用户连续发送多条消息时，Airi 在用户发送完成前抢答。
2. 消息只提到 Airi、转述 Airi 或讨论 Airi 时，被错误当成对 Airi 说话。
3. 回复只使用有限的知识标签命中，不能按当前对话检索知识、用户印象、群印象和历史对话。

## 约束

- 所有消息统一等待 10 秒，不为 @ 或回复入口设置立即处理例外。
- 受话判断必须包含在正式对话调用中，不增加独立的受话分类模型调用。
- 总体说话频率沿用现有概率策略，不让模型的语义判断直接替代概率控制。
- 不引入向量数据库、embedding 服务或新的部署依赖。
- 保留现有记忆文件格式和旧存档兼容能力。
- 用户可见提示、日志和 Bot 消息继续使用中文；代码不添加 docstring 或 comment。

## 总体方案

采用“10 秒批处理 + 一次结构化对话调用 + 本地候选压缩”的混合方案。

消息到达后先按群号和用户 QQ 号进入待处理批次。批次在最后一条消息到达后等待 10 秒，等待期间继续到达的同一用户消息会追加到原批次并重新计时。计时结束后，按消息原始顺序保存上下文，并执行一次正式对话调用。

正式对话调用同时完成：

- 综合当前批次、最近对话、引用关系、说话人和称呼信息判断是否在对 Airi 说话；
- 从候选背景中判断与当前消息相关的内容；
- 生成回复正文和可选的引用目标。

代码根据调用返回的受话结果继续执行现有的说话概率门控，只有概率允许且正文非空时才发送。

## 消息批处理

### 批次键和生命周期

- 批次键：`(group_id, user_id)`。
- 每个键最多有一个等待任务和一个待处理消息列表。
- 新消息追加到列表，取消旧等待任务，创建新的 10 秒等待任务。
- 等待任务结束后原子取出当前列表，形成不可变快照，再开始正式处理。
- 快照开始处理后到达的新消息进入下一批，不修改正在处理的快照。

### 批次内容

每条消息保留独立的 `ContextEntry` 信息：文本、图片占位、消息 ID、引用 ID、昵称、QQ 昵称和时间戳。正式对话输入另外提供一个按顺序拼接的“当前消息批次”段，避免模型把同一用户的连续发送误看成互不相关的多轮对话。

所有消息仍只保存一次上下文。批次中的每条消息保留独立消息 ID，以支持回复目标校验。

### 并发和退出

- 同一群的正式回复继续使用现有群锁，避免多个批次同时发送。
- 等待任务被取消时静默结束，不产生错误日志。
- 插件关闭时取消并清理全部等待任务；已取出的快照不再启动新的发送流程。

## 统一对话调用协议

正式对话调用使用现有结构化 LLM API。角色提示词和上下文作为输入，追加内部协议，要求只返回 JSON：

```json
{
  "addressed": true,
  "reply": "回复正文",
  "reply_to": "消息ID或空字符串",
  "used_context": ["候选片段ID"]
}
```

字段约束：

- `addressed` 表示模型综合判断当前批次是否在对 Airi 说话。直接 @、回复 Airi、上下文承接、称呼和语义关系都是判断依据；单纯提及、转述或讨论 Airi 不自动视为受话。
- `reply` 是不含 JSON、协议字段和内部说明的普通回复正文。为空表示不生成回复。
- `reply_to` 只能填写当前上下文中非 Airi 自己消息的有效消息 ID；非法 ID 被代码丢弃。
- `used_context` 只能填写候选列表中的片段 ID，用于更新知识命中计数和诊断，不作为用户可见内容。

正式调用失败、结构化结果无法解析或字段不合法时，本轮不发送，不把失败误判成“用户没有对 Airi 说话”。

主动插话使用同一生成器，但输入模式明确为主动发言，跳过受话判断，要求从历史对话中接一个具体内容；现有主动插话概率和延迟保持不变。

## 说话频率控制

模型只负责产生 `addressed`，代码继续负责概率控制：

- `addressed=true`：沿用被点名的 `ADDRESSED_PROB`、好感度加成和现有冷却逻辑。
- `addressed=false`：沿用未被点名的基础概率、流量、心情、精力和时段乘数。
- `addressed` 不会直接强制发送，也不会直接禁止现有低概率主动聊天。

这样可避免结构化协议把 Airi 变得过于沉默。可见变化是同一用户 10 秒内的多条消息合并为一次处理和最多一次回复。

## 统一检索候选

在正式对话调用前构建候选片段，来源覆盖所有可影响回复的机制：

1. 群知识库：事实、术语、群规、活动规律、群内典故。
2. 用户印象：QQ 昵称、群内外号、长期印象和可用于理解关系的背景。
3. 群印象：群长期概要。
4. 对话记忆：滚动概要、最近原始消息、引用目标和当前消息批次。
5. 话题和环境：当前话题、群表达风格、Airi 心情、Airi 精力和时间状态。

本地候选压缩使用关键词、用户 ID、实体、引用关系、时间新鲜度和来源优先级，限制总候选数量后交给正式对话调用统一判断。知识条目的命中计数仅对 `used_context` 中实际使用的知识片段递增。

注入规则：

- 事实、群印象、用户印象和历史对话只在与当前批次直接相关时注入。
- 心情、精力、表达风格和时间继续标记为只影响措辞，不得成为回复主题。
- 候选缺失、检索无命中或检索过程异常时，正式对话仍使用基础最近对话上下文。

## 错误处理和兼容性

- 旧 `KnowledgeEntry`、`GroupContext`、`UserMemory` 和长期记忆 pickle 继续按现有归一化逻辑加载。
- 未完成批次不会写入新的持久化结构；消息保存仍使用已有上下文格式。
- 结构化模型不支持 `response_format` 时沿用现有纯文本 JSON 回退。
- LLM 降级链、空回复处理和群锁语义保持不变。
- 检索候选过多时截断，不阻塞消息主循环。

## 验证计划

### 批处理

- 同一用户连续发送 2～5 条消息只形成一个批次，内容和顺序完整。
- 每次新消息都会重置 10 秒计时；计时边界不提前触发。
- 不同用户在同一群可并行等待；正在处理的批次不被新消息改写。
- 直接 @、回复和普通消息都等待 10 秒。

### 受话判断和频率

- 直接 @ 或回复在上下文相关时判定为受话。
- 仅提到 Airi、转述 Airi、讨论 Airi 或引用角色名字不自动判定为受话。
- 受话结果为真和假时分别走现有高概率、低概率门控。
- 结构化调用失败时不发送，且不改变负面说话令牌和上下文完整性。

### 检索

- 分别验证知识、用户印象、群印象、滚动概要、历史消息、引用关系和当前话题候选能被提供给正式对话调用。
- 验证不相关候选不会被注入回复背景。
- 验证 `used_context` 只更新合法知识条目命中数。
- 验证检索无命中或失败时仍能正常生成普通回复。
