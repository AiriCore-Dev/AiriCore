# 心愿瓶图片文件化存储设计

## 目标

将 `airi_wish_bottle` 的持久化图片从 `data.pk` 内嵌 base64 改为独立文件。每张图片存放在 `data/airi_wish_bottle/images/` 下，读取时直接从磁盘加载，不接入 AiriCore 缓存机制。心愿瓶或待审核版本被销毁、替换或拒绝时，同步删除不再使用的图片文件。

## 存储结构

新增 `plugins/airi_wish_bottle/base/image_store.py`，集中处理图片写入、读取、迁移、删除和孤儿清理。

图片目录：

```text
data/airi_wish_bottle/images/
```

每张图片使用随机 32 位十六进制文件名，并保留由图片魔数识别出的扩展名：

```text
8fc3c5e3df8c4da3a69697a888e1f3ad.png
```

存档不保存绝对或相对文件路径，只保存逻辑引用：

```text
image://8fc3c5e3df8c4da3a69697a888e1f3ad.png
```

`images` 列表和 `segments` 中的图片段使用相同逻辑引用。读取逻辑只接受严格匹配随机文件名格式及允许扩展名的引用，拒绝目录分隔符、路径穿越和未知格式。

## 写入流程

消息接收与机器审核阶段继续使用内存中的 `base64://` 图片，不提前写盘。

审核结果确定且心愿瓶编号可用后：

1. 解码并重新验证每张图片的大小、魔数和允许格式。
2. 在图片目录创建临时文件，完整写入并刷新后使用 `os.replace` 原子改名。
3. 按图片出现顺序生成 `image://` 引用，并同步替换 `images` 与 `segments`。
4. 全部图片写入成功后才修改 `state.data`。
5. 任一图片失败时删除本次已创建的文件，不修改状态，并向用户返回中文失败提示。

所有文件 I/O 通过 `asyncio.to_thread` 执行，避免在事件循环中同步读写最多 9 张、单张最多 5MB 的图片。

## 无缓存读取

`image_store.py` 不导入 `cache_mode`、`asset_cache`、`ByteLRU` 或其他缓存模块。

`bottle_content_message` 改为异步。每次拾取心愿瓶时，它直接读取对应图片文件、验证内容并转换为 `base64://` 后交给 `MessageSegment.image`。同一张图片每次拾取都会重新读盘，不保留 Python 内存缓存。

旧存档中尚未迁移成功的 `base64://` 图片继续直接使用。文件缺失、损坏或引用非法时记录中文日志，并在原图位置加入“【图片读取失败】”，不令整条心愿瓶消息发送失败。

## 生命周期与删除

图片文件采用单记录独占的随机文件名，不做跨瓶去重，因此删除不需要引用计数。

### 正式心愿瓶

- 用户执行“销毁心愿瓶”时，移除瓶子记录并删除其 `image://` 文件。
- 举报审核成立时复用同一删除入口，因此同时删除图片。
- 直接修改成功时，先完整写入新图片并替换记录，再删除旧图片。
- 图片删除失败只记录日志，瓶子销毁或修改结果不回滚，避免残留文件阻塞业务；孤儿清理会在后续启动重试。

### 待审核心愿瓶

- 新瓶或修改未通过机器审核时，图片写入独立随机文件，并由 `pending_bottles` 引用。
- 同一瓶再次提交待审核修改时，先写入并切换到新版本，再删除旧待审核版本图片。
- 人工审核拒绝单个或全部待审核瓶时，删除对应图片。
- 人工审核通过时，待审核图片引用直接成为正式记录的一部分，不重复写文件。
- 若审核通过的是已有瓶子的修改版本，成功替换后删除原正式版本图片。
- 若审核通过时因编号归属冲突生成新编号，随机图片引用无需改名。

状态变更与文件清理遵循“新文件先落盘、记录再切换、旧文件最后删除”的顺序，确保失败时旧版本仍可使用。

## 旧数据自动迁移

在 `load_json` 成功载入存档后扫描 `bottles` 与 `pending_bottles`。

- 首次发现 base64 图片时，在同目录创建一次性迁移前备份 `data.pk.pre-image-files.bak`。
- 逐张将 `images` 中的 `base64://` 图片写入独立文件，并按图片出现顺序同步替换 `segments` 中对应图片段。
- 成功迁移的图片从 `data.pk` 中移除 base64，仅保留 `image://` 引用。
- 单张迁移失败时保留该图片原始 base64，记录日志并允许下次启动重试；同一记录可暂时同时包含文件引用与旧 base64。
- 旧记录没有 `segments` 时保持 `content + images` 兼容路径。
- 存在迁移改动时，迁移后的存档写入成功后才执行孤儿文件清理；保存失败时保留新文件和当前内存引用，不清理图片目录。没有迁移改动时，成功加载的存档可直接作为孤儿清理的引用依据。

迁移不依赖当前本地数据是否为空，适用于已有实际部署存档。

## 孤儿文件清理

存档加载成功后，收集正式瓶与待审核瓶引用的全部合法 `image://` 文件名，删除图片目录中未被引用的合法图片文件。若本次发生迁移，则必须先确认迁移后的存档保存成功。

以下情况禁止孤儿清理：

- `data.pk` 与备份均加载失败。
- 当前运行处于坏档写保护状态。
- 迁移后的存档保存失败。

临时文件由写入失败路径即时删除；启动清理同时删除遗留的本模块临时文件。

## 数据与接口调整

- `images` 从持久化 base64 列表改为逻辑引用列表，但读取端继续兼容 `base64://`。
- `segments` 图片段同样改为逻辑引用，并继续保持图文顺序。
- `bottle_content_message` 改为异步，拾取 handler 使用 `await`。
- 图片删除入口改为异步，用户销毁和举报审核入口全部使用 `await`。
- `add_bottle` 继续只负责状态与 `collections` 更新；文件写入和旧文件清理由 handler 与审核流程在状态切换前后协调。
- `save_to_json` 返回本次存档写入是否成功，供迁移与孤儿清理决定是否继续。

## 错误处理

- 新图片写入失败：删除本次新文件，保持旧记录不变，并提示“图片保存失败，请稍后再试”。
- 图片读取失败：记录路径安全或文件错误，在原位置显示“【图片读取失败】”。
- 删除失败：记录文件名和异常，业务记录仍按用户操作删除或替换，等待启动孤儿清理重试。
- 迁移失败：保留原 base64，不删除旧数据，不阻塞插件启动。
- 存档加载失败：沿用现有坏档保护，禁止迁移、写入和孤儿清理。

## 测试与验证

使用任务内临时测试脚本按 TDD 执行，完成后删除脚本及其缓存。覆盖：

- 单张和多张图片原子写入，扩展名与逻辑引用正确。
- 路径穿越、非法文件名、未知格式和超限图片被拒绝。
- 修改磁盘文件后再次读取能观察到变化，证明没有内存缓存。
- 图文顺序读取、旧 base64 兼容、文件缺失占位。
- 新瓶直发、待审核新瓶、直接修改、待审核修改和审核通过的数据引用正确。
- 用户销毁、举报成立、单个拒绝、批量拒绝、待审核版本替换均删除对应文件。
- 新文件写入失败时状态不变且部分文件回滚。
- 旧存档迁移成功、部分失败保留 base64、迁移前备份和保存失败保护。
- 孤儿清理只在安全条件下执行，坏档状态不删除图片。
- 插件加载、`compileall`、聚焦 Ruff 与 `git diff --check` 通过。

## 非目标

- 不接入或扩展全局 `cache_mode`。
- 不对图片做跨瓶去重、缩放、重编码或质量压缩。
- 不改变图片数量、单图大小、支持格式或内容审核规则。
- 不把本地文件路径直接发送给 OneBot；发送前仍转换为 base64。
