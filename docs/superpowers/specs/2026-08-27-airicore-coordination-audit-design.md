# AiriCore 全仓协调性审计、缺陷修复与算法优化设计

## 目标

对 AiriCore 当前工作区进行一次可复验的全仓审计，修复能够由测试或源码契约确认的 bug，并优化有证据的算法与资源热点。首要目标是提升整体协调性：插件与共享基础设施之间、插件与插件之间在启动、事件处理、后台任务、消息发送、状态持久化和错误传播方面具有一致且可测试的行为。

## 范围与约束

- 覆盖 `bot.py`、`utils/`、`plugins/`、部署脚本和项目配置；运行时数据、日志、生成素材不纳入源码重构范围。
- 保留工作区已有的 LLM 未提交修改，不回滚、不覆盖；新改动与其兼容。
- 不引入大型事件总线，不改变 NoneBot 事件模型，不把插件内部状态暴露为跨插件公共 API。
- 代码不新增 docstring 或 comment；用户可见文本保持中文。专有名词规则为：“桃井爱莉”必须保持完整；除此之外使用 `AiriCore` 或 `Airi`，禁止拼接出“桃井Airi”等混合表达。
- 每个生产修复必须先有最小失败测试并观察到预期失败；测试完成后删除临时验证脚本和产物。

## 协调性模型

建立最小共享协调层，优先复用现有 `utils` 模块：

1. 任务生命周期：统一登记后台任务、保存任务句柄、在 shutdown/disconnect 时可取消并等待，避免插件各自遗留 `create_task`。
2. 消息与 Bot 选择：统一目标捕获、配置 Bot 优先级、跨 Bot 回退和错误上下文，避免插件自行扫描 `get_bots()` 产生不一致。
3. 共享状态：明确锁的粒度、所有权和释放时机；跨插件桥接只接受不可变快照或显式方法，不直接读写对方内部字典。
4. 持久化契约：统一加载失败、版本迁移、原子写入、flush 和 shutdown 顺序；失败时内存状态与磁盘状态的回滚语义必须明确。
5. 错误上下文：日志包含插件、Bot、会话/群组和操作标签；可恢复错误返回统一结果，取消异常继续向上传播。

协调层只提供薄接口，插件仍负责业务规则。已有成熟实现优先收敛为公共接口，避免平行抽象。

## 审计阶段

### 1. 基线与清单

定位项目实际 Python 运行时，执行编译检查、Ruff 致命规则、插件导入/加载、现有测试和 git diff 检查。NoneBot 动态测试固定使用 `/opt/homebrew/Caskroom/miniconda/base/envs/airidev/bin/python`，先执行 `nonebot.init()`，注册 OneBot V11 适配器，再先加载 `nonebot_plugin_apscheduler` 等依赖插件后加载目标插件。输出插件数量、失败模块、后台任务入口、跨插件导入和共享持久化点清单。

### 2. 静态协调审计

检查启动依赖顺序、可选依赖、重复 matcher、未保存的后台任务、未限制的并发、锁顺序反转、跨群/跨 Bot 状态泄漏、异常吞噬、同步 I/O 阻塞事件循环、pickle/路径/网络边界和明显的 O(n²) 或无界循环。每项记录触发条件、影响范围和证据。

### 3. 动态复现与假设验证

对高风险项建立最小场景：多 Bot 同群、插件启动/卸载、断线重连、并发写入、取消与超时、坏档迁移、跨插件回退发送。一次只验证一个根因，未复现的问题不直接修改。

### 4. TDD 修复与优化

按影响排序逐项执行 RED-GREEN-REFACTOR。先处理会造成连锁故障的生命周期、竞态、资源泄漏和错误传播，再处理局部功能 bug。算法优化必须提供前后复杂度、耗时、内存或任务数量证据，避免借审计之名进行无关重构。

### 5. 全量验证

重新执行全仓 compileall、Ruff、插件加载、专项回归和关键资源稳定性检查；对协调层验证任务无泄漏、锁最终释放、持久化可恢复、Bot 选择一致、错误日志可归因。无法运行的检查明确记录环境原因和残余风险。

## 接口与数据流约定

- 插件调用共享能力时只依赖公开函数和不可变输入，禁止导入另一个插件的私有全局变量。
- 事件处理器在创建后台任务时必须登记任务，并绑定会话/插件标识；任务异常必须被记录，取消必须可等待。
- 跨插件调用返回明确的成功/失败/取消结果；网络或 Bot 发送失败不得静默吞掉，也不得在锁内长时间等待外部 I/O。
- 状态更新遵循“锁内校验与提交、锁外 I/O、失败反向恢复”的顺序；持久化文件使用原子替换。
- 所有新增回归测试集中在既有测试位置或临时目录，验证完成后清理临时文件。

## 验收标准

1. 每个修复都有可重复的失败测试、通过测试和影响说明。
2. 全仓静态检查与插件加载无新增错误，现有未提交 LLM 改动保持可用。
3. 关键协调场景下不存在未回收后台任务、永久持有锁、跨 Bot 错发、跨群状态污染或持久化半写入。
4. 性能优化有可比较的基线数据或严格复杂度论证，且行为兼容旧数据和旧指令。
5. 完成后新增或更新项目记忆文件及 `MEMORY.md` 索引，记录未解决风险和验证环境。

## 不在本轮范围

- 将整个系统改造成事件总线或微服务。
- 修改外部 API 协议、网页客户端权威性或需要生产凭据的行为。
- 因风格偏好进行无测试支持的批量重命名、目录重排或格式化。
