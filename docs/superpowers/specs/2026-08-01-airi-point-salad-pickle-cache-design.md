# Airi Point Salad 持久化、缓存与可读性设计

## 目标

- 将得分沙拉对局存档从 JSON 切换为 pickle。
- 保留现有状态模型校验、原子写入、备份恢复和坏档隔离能力。
- 让插件生成的稳定图片组件遵循全局 `ram`、`balanced`、`disk` 缓存模式。
- 不让缓存模式影响对局数据持久化，避免 `disk` 模式丢失进行中的游戏。
- 提高桌面图、牌背图标和文字在手机聊天预览中的可读性。
- 在玩家轮次开始时，用一条消息同时发送玩家提醒和桌面图片。

## 非目标

- 不缓存完整桌面图或结算图。
- 不改变游戏规则、指令、信息内容或超时逻辑。
- 不直接 pickle `GameState` 等 Python 类实例。
- 不改变全局缓存配置项或现有共享缓存实现。

## 存档格式

主存档改为 `data/airi_point_salad/games.pk`，备份为 `games.pk.bak`。pickle 内容保持为 `{群号字符串: GameState.to_dict() 结果}`，写入时使用 `pickle.HIGHEST_PROTOCOL`，读取后仍逐项调用 `GameState.from_dict()`。

这种结构满足 pickle 存储要求，同时避免存档绑定数据类的模块路径和内部布局。状态字段继续经过现有严格类型检查，损坏或结构不合法的数据不会进入运行时状态。

写入流程维持现有事务语义：先在同目录创建临时文件，写入并 `fsync`，再复制旧主档为备份，最后用 `os.replace` 原子替换主档。临时文件使用 `.pk` 后缀，失败时删除。

## 旧 JSON 迁移

当 `games.pk` 不存在时，加载器检查旧 `games.json`。旧档使用现有 JSON 规则解析并经过 `GameState.from_dict()` 校验；主档失败时继续尝试 `games.json.bak`。成功恢复后立即原子写入 `games.pk`，后续只使用 pickle。

迁移不会删除或覆盖旧 JSON 文件，便于人工回退。旧主档与备份均损坏时，沿用坏档隔离策略，将存在的旧主档改名为带时间戳的 `games.corrupt.*.json` 文件并返回空状态。

正常 pickle 加载时先读主档，再读 `games.pk.bak`。两者均失败时隔离 pickle 主档为带时间戳的 `games.corrupt.*.pk` 文件并返回空状态。

## 渲染缓存

插件增加一个基于 `ByteLRU` 的进程内渲染缓存，并通过 `register_cache` 注册为 `point_salad.rendered`，使其出现在统一缓存统计中。缓存使用全局 `images` 字节预算，保存以下可重建组件：

- 六名角色的完整角色卡面，以角色枚举为键。
- 计分卡面，以卡片 ID 和完整计分规则签名为键。
- 圆形角色头像，以角色枚举和尺寸为键。

计分规则签名包含规则类型、角色列表、分值、惩罚值和比较关系，避免相同卡片 ID 在规则发生变化时复用错误图片。

缓存只保存内部图片对象。所有命中和新建结果对调用方都返回副本，防止 `thumbnail`、`resize`、`alpha_composite` 等 Pillow 操作污染共享对象。完整桌面图和结算图随对局状态频繁变化，不进入缓存。

## 三种缓存模式

- `ram`：关闭插件内 LRU 字节上限，首次生成后驻留；仍通过全局 resident ledger 服从 `cache_preload_budget_mb` 总预算。
- `balanced`：使用 `get_cache_budget_bytes("images")` 上限，并启用 `ByteLRU` 二次访问准入与 LRU 淘汰。
- `disk`：每次调用前清空插件渲染缓存，并直接重新生成图片，不读取或写入缓存。

静态源图片和字体继续通过已有 `utils.asset_cache` 读取，因此它们原有的三模式行为保持不变。模式仍在启动时确定，切换后需要重启。

## 桌面与牌背可读性

桌面继续使用单图输出，不拆分市场和玩家信息。画布宽度从 `1350px` 提高到约 `2160px`，高度继续根据模式、玩家数和当前玩家持有的计分牌数量动态增长。

三列市场保留横向排列。市场中的计分牌从 `250×350px` 放大到约 `432×605px`，角色牌放大到约 `252×353px`，并重新分配三列间距、槽位编号位置和上下区块间距。市场、Mission、玩家列表和当前玩家持牌区依次向下排布，避免放大后互相覆盖。

牌背原图保持 `750×1050px`，但内部元素提高相对占比：

- 角色图标由 `130px` 放大到约 `204px`。
- 规则文字由 `44px` 提高到约 `72px`。
- 分值文字由 `76px` 提高到约 `120px`。
- 标题、图标、规则和分值重新纵向排布；三角色规则仍必须完整容纳，不发生裁切或重叠。

桌面中的页眉模式文字、回合信息、当前玩家、Center 状态、列标、槽位编号、Mission、玩家摘要、持牌明细和底部指令都提高相对字号。目标字号分别落在 `32px` 至 `70px` 区间，最小的持牌明细和底部指令不低于 `32px`，确保它们在更大画布中不会因等比缩放而继续维持原有的小字占比。

桌面仍编码为 JPEG 并通过 `base64://` 发送。质量从高到低自适应调整，以保持单图不超过 `3 MB`；不得通过降低上述目标分辨率来满足体积限制。完整桌面和结算图仍不进入缓存，缓存保存的是 `750×1050px` 原始卡面组件，桌面组合阶段再缩放到目标尺寸。

## 轮次开始提醒

仅在新的玩家轮次开始时提醒该玩家，触发条件为：

- 游戏从大厅进入进行中状态，首位玩家的第一回合开始。
- 当前玩家成功完成行动，游戏仍在进行中，并切换到下一位玩家。

翻计分牌、准备或执行未结束回合的 Center 技能、查看桌面、查看规则、加入、退出和创建房间都不触发提醒。最后一次行动使游戏直接进入结算时也不提醒下一位玩家。

服务层在持有群锁并完成状态变更后，对比变更前后的阶段与当前玩家 ID，生成可选的 `turn_user_id`。只有保存成功并确认事务未回滚后，适配层才发送提醒。

存在 `turn_user_id` 且响应是桌面图片时，适配层把 `MessageSegment.at(turn_user_id)` 和 `MessageSegment.image(base64)` 组合成同一个 OneBot 消息后发送，不拆成两条消息。其他图片与文本响应保持原有发送方式。

## 错误处理与并发

`GameStore` 继续使用异步保存锁，磁盘序列化放入工作线程，不阻塞事件循环。渲染缓存依赖 `ByteLRU` 自身的线程锁；多个群同时首次请求同一组件时允许重复构建，但最终缓存内容等价，不扩大锁的临界区。

存档读取、备份恢复、迁移和隔离日志继续使用中文。任何保存异常保持向上传播，使 `GameService` 恢复变更前状态，不改变现有事务回滚保证。

## 验证

测试先于实现，并覆盖：

- pickle 写入内容为纯字典，能够严格往返恢复完整 `GameState`。
- pickle 主档失败时从备份恢复，主备均失败时隔离 `.pk` 主档。
- 无 pickle 时从 JSON 主档迁移，JSON 主档失败时从旧备份迁移。
- `ram` 首次生成后命中缓存，返回对象互不共享可变状态。
- `balanced` 第一次跳过、第二次准入、后续命中，并受字节预算约束。
- `disk` 始终重新生成并清空已有插件渲染缓存。
- 卡片规则签名不同不会错误命中同一计分卡面。
- 牌背图标、规则文字和分值达到目标尺寸，三角色规则不裁切、不重叠。
- 最坏桌面达到约 `2160px` 宽，所有动态区块不重叠，最小正文不低于 `32px`。
- 真实卡面、桌面和结算渲染能够产生可解码且不超过 `3 MB` 的 base64 JPEG。
- 首回合和玩家切换各产生一次 `@玩家 + 图片` 的单条消息，未结束回合的操作和主动查看桌面不产生提醒。
- 保存失败并回滚时不发送轮次提醒，游戏结算时不产生无效提醒。
- 插件加载、Python AST、编译、Ruff 和差异检查通过。
